# Final log-table rollout

This completes [mirror setup](LOG_PARTITION_MIRRORS.md) for `session_logs`,
`api_request_logs`, and `change_logs`. Flow logs remain partitioned with their
existing 121-day retention. The other three streams keep the full UTC day
starting 90 days ago, with 14 days of future partitions.

Deploying this release does not backfill or switch a table. The application
supports both layouts, independently per stream. Keep all three mirror triggers
active until cutover. Do not change source/mirror schemas independently or write
directly to mirrors during this procedure.

## 1. Deploy and prepare

Deploy this release and wait for the previous instances to drain. In particular,
all change-log consumers must be running this release before cutting over
`change_logs`: older consumers only support the original LSN conflict target.
The usual approximately 30-second overlap can happen before these steps.

Run pending manual migrations from the release IEx shell:

```elixir
Portal.Release.migrate(manual: true)
```

Inspect pending manual migrations first; this runs all of them. The new migration
`20260928000000_prepare_log_table_cutover.exs` only creates a small checkpoint
table, using a one-second lock timeout. It performs no data copy or rename.
It also works when the preceding mirror migration is still pending.

Ensure `Portal.Workers.PartitionLogTables` has run successfully and all mirrors
are active before starting. There must be room for both copies and the extra
WAL generated by backfill. Monitor write latency, replica lag, disk usage and
Oban failures while it runs.

## 2. Start or resume backfill

```elixir
%{"batch_size" => 500}
|> Portal.Workers.BackfillLogTables.new()
|> Oban.insert()

Portal.LogTableMigration.status()
```

The job processes one batch per stream, commits each batch with its checkpoint,
and snoozes for one second between runs. Each pass captures a finite upper
primary key, then uses indexed `(account_id, log_id)` keyset pagination. New
writes beyond that upper key are already covered by the transactional triggers.
`scanned_rows` includes expired rows inspected and skipped; `verified_rows`
counts keys inspected across both verification passes. These are progress
counters, not estimates of the remaining work.

The phases are `copy`, `verify_source`, `verify_mirror`, `analyze`, and `ready`.
Copy locks source rows before reading their current values and upserts the
entire stored row, preserving IDs, timestamps, and `seq`. Identical mirror rows
are not rewritten. It never skips locked rows. An MCP update, retention delete, or account deletion therefore cannot be
silently overwritten or resurrected by a stale backfill snapshot. Expired rows
advance the cursor without requiring expired partitions.

Verification compares complete rows in both directions using a single SQL
snapshot per batch. Missing, divergent, and extra retained mirror rows stop the
job. After verification, `ANALYZE` refreshes replacement statistics before the
cutover. No full-table scan runs under the cutover's exclusive locks.

A failed batch rolls back its checkpoint and can be retried. There is a
one-second lock timeout and a ten-second statement timeout for batches; ANALYZE
has a separate 110-second budget. If the default batch size causes contention,
cancel the Oban job and enqueue one with a smaller batch size (1–2000). It resumes
the same checkpoints. Retry a discarded job after resolving its failure.

For a controlled single batch from IEx:

```elixir
Portal.LogTableMigration.step("session_logs", 100)
```

`:progress` means more work remains; `:ready` means verification and ANALYZE
finished; `:busy` means maintenance or another migration operation holds the
shared advisory lock. Each batch rechecks activation, trigger definition, and
column/default compatibility. Changed activation or definitions restart the
passes; disabled/missing mirroring or incompatible columns stop progress.
Investigate a verification error before retrying. To recopy after repairing a
divergence, cancel the backfill job and delete only that stream's checkpoint
before cutover, then enqueue the job again:

```sql
DELETE FROM log_table_backfills
WHERE source_table = 'session_logs' AND cutover_at IS NULL;
```

There is no need to wait 90 days after mirror activation: the backfill fills the
retained history immediately. Runtime depends on table size and database load;
the local integration tests do not estimate production throughput.

## 3. Cut over each verified stream

Check `Portal.LogTableMigration.status()` and expect `ready` for each stream.
Cut over one at a time from IEx, inspecting each result:

```elixir
Portal.LogTableMigration.cutover("session_logs")
Portal.LogTableMigration.cutover("api_request_logs")
Portal.LogTableMigration.cutover("change_logs")
```

Each call returns `:cutover` (or `:already_cut_over` on a retry). `:busy` means
retry later. A lock timeout raises and rolls back the entire transaction; the
original names and checkpoint remain unchanged. Investigate long-running
queries/transactions before retrying. Do not wrap these calls in another
transaction.

Within a short transaction, cutover:

1. Takes the same advisory lock as partition maintenance and backfill.
2. Takes exclusive locks on the original and replacement parents, with a
   one-second lock timeout. Traffic can wait briefly while these locks are held.
3. Rechecks verified readiness against the current activation, trigger and
   schemas. Foreign keys referencing the source, dependent views, and logical
   publications block cutover and require a separate dependency migration.
4. Renames the source to `*_legacy` and the replacement to the canonical name.
5. Transfers ownership of the original `seq` sequence to the replacement.
6. Retargets the legacy trigger to the new canonical table and records cutover.

There is no bulk copy or index build during this transaction. Brief lock waits
are expected; this avoids a maintenance outage but cannot promise zero request
latency impact on a busy database. PostgreSQL invalidates prepared statements
for altered relations. The retained forward trigger also bridges writes that
still address the legacy relation during the transition.

The change-log consumer resolves the conflict target while holding a lock on
the canonical relation: `(lsn)` before cutover, `(timestamp, lsn)` afterwards.
After cutover, it discards WAL records older than retained partitions. API MCP
updates retain their original `inserted_at` predicate. API changesets match the
account FK suffix so legacy and partition constraint names both map to errors.
Log-sink cursors need no
reset because historical sequence values and their original sequences survive.

Partition maintenance automatically follows each renamed parent while retaining
the existing `*_partitioned_YYYYMMDD` child names. It remains the single scheduled
maintenance worker. Legacy DELETE jobs become no-ops for each partitioned
canonical table; partition detach/drop now handles retention. The replacement
indexes omit the original timestamp-first retention index.

## 4. Validate, then remove legacy tables

Exercise all three log views, a REST request and a multi-stage MCP request.
Check change-log replay/consumer health, log-sink delivery, and partition worker
success. Review query plans and timings with production-like data; partitioning
alone does not add a substring-search index or eliminate expensive all-history
filters/counts.

Keep legacy tables until the application pools that spanned cutover have been
recycled/drained and the new layout has been validated. The forward bridge
covers transitional legacy writes, but **new canonical writes do not update the
legacy copy**. It is not a rollback target. Do not rename it back or deploy an
old release whose change-log consumer lacks the composite conflict target.
Before any cutover, reverting the application leaves the original layout intact;
after cutover, rollback requires preserving writes accepted by the new tables.

After validation, explicitly remove each legacy table from IEx:

```elixir
Portal.LogTableMigration.cleanup("session_logs")
Portal.LogTableMigration.cleanup("api_request_logs")
Portal.LogTableMigration.cleanup("change_logs")
```

Cleanup checks recorded table identities, takes the migration advisory lock,
and drops the legacy table and its bridge function without CASCADE. A dependency
or lock timeout aborts cleanup. Retry after investigating. The original sequence
is owned by the new parent, so dropping the legacy table cannot drop it. Cleanup
is idempotent and records `legacy_dropped_at`. Checkpoints and activation metadata
remain available for audit; no read or write path depends on legacy tables.

Do not roll back either manual migration after cutover. The checkpoint migration
refuses rollback when it contains a cutover record.
